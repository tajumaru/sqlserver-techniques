# デッドロック調査手順

同じテーブルに対して、複数の業務が同じ時間帯に UPDATE / DELETE / INSERT を流してデッドロックする、という形を想定した調査手順。

## 想定ケース

- 対象は1テーブル。主キー（業務キー）で絞る処理同士が衝突する
- 主キーの値は業務ごとに違う（例: A業務は 1001、B業務は 1002）のにデッドロックする
- 同じ時間帯にバッチが重なる

主キーの値が違う業務同士でも、検索範囲や他のインデックスでロック対象が重なることがある。記録とその場の観測を合わせ、どのリソースで待ち合ったかを調べる。

主キーが WHERE の定数ではなく、INNER JOIN や EXISTS で相手表から渡ってくる形もある。この形では、プランの形（シーク中心か、ハッシュ結合＋走査か）が両側の結合列・絞り込み列の統計に強く依存する。統計の鮮度確認（10）は対象テーブルだけでなく、結合相手のテーブルにも実行する。また、同じ表同士に触るバッチでも、触る順番がバッチごとに逆だと統計とは無関係にデッドロックし得る（ロックの取得順）。プランの形と合わせて、バッチごとのアクセス順も見る。

## 手順

1. **記録を抜く** — `queries/05-deadlock-history.sql`
   system_health（既定で記録されている）からデッドロックグラフを含むイベント XML を取得する。ring_buffer は古い記録から消え、XML 変換の上限でも欠落するため、発生に気づいたら先に取得して保存する。

2. **要約して合流点を見る** — `queries/06-deadlock-summary.sql`
   結果3（リソースの一覧）が中心。`index_name` と `resource_type` を手がかりにする。外部共有時は結果2の SQL 文面・ログイン名・アプリ名を伏せる。

   | 結果3 の姿 | 型 | 次に見るもの |
   |---|---|---|
   | index_name が主キー、resource_type = KEY | 主キーのキーを待ち合った記録。条件や処理範囲が重なる可能性を調べる | 各業務の WHERE の実範囲 |
   | index_name が非クラスタ化インデックス | そのインデックス上の待ち合い。状態・区分・日付など値の種類が少ない列では、同じキーやページに処理が集まる場合がある | 07 でそのインデックスのキー列と、UPDATE がその列を書き換えるか |
   | resource_type = PAGE | ページ単位の待ち合い。処理が触れる範囲を調べる | 09 でプランのシーク判定 |
   | resource_type = OBJECT（テーブルロック） | オブジェクト単位の待ち合い。昇格の有無は別途確認する | 処理件数とコミット単位 |

3. **インデックスの詳細を確認する** — `queries/07-table-index-detail.sql`
   対象テーブルの全インデックス（キー列・包含列・行数）。低基数列の非クラスタ化インデックスと、UPDATE の書き換え対象列が含まれるインデックスが候補。使用実績は `queries/04-index-usage.sql` で裏取りする。

4. **プランがシークか確認する** — `queries/09-plan-cache-by-table.sql`
   主キーで絞るはずの処理がスキャンになっていないか。暗黙の型変換で Seek が落ちていないかは `queries/02-implicit-conversion.sql` も併用する。

5. **再現時間帯にライブで見る** — `queries/08-live-locks.sql`
   バッチが重なる時間帯に実行し、どのインデックスにどのモードのロックが集中しているか、ブロックの姿を捉える。グラフとその場の観測を照らし合わせ、共通するリソースや処理を探す。取得順や原因は追加の観測と合わせて確認する。

## データを持ち出せない環境では

お客様のデータなど、グラフや SQL 文面を環境の外に出せない場合は `queries/11-deadlock-verdict.sql` を使う。合流点・プラン・統計をサーバー内で調べ、件数・割合・判定・統計の最終更新日時を返す。別 DB の表が合流点なら、その DB に接続して再実行するよう案内する。表を一意に特定できない、対象のプランが見つからない、統計を取得できない場合などには「未確認」が残る。結果を外部共有する際はインデックス名を伏せる。

## 対策（型が分かったあと）

効く順の目安:

1. **処理順を業務間で揃える** — 主キーの昇順など共通の順で、小さく刻んで処理する。実際にロックを取得する順序はプランや他の操作も含めて確認する。固定する具体形：対象キーを先に一時テーブルへ集め（この段階では相手表は読み取りだけ）、書き込みはキー表から駆動して主キー順に行う。JOIN 直書きと EXISTS では駆動側が逆になりやすいので、両バッチをこの形に寄せると順番が揃う。すでにキー表の形でも、キー列に主キーが無ければ格納順は不定で、書き込みプランがハッシュ結合＋走査なら処理順は固定されない。キー表のキー列に主キー（クラスタ化）を付け、書き込みがシークで駆動されているかプランで確認する
2. **シーク化する** — WHERE に合うインデックス、パラメータの型の一致。掴む行が減れば衝突自体が減る
3. **コミットを刻む** — 1トランザクションの行数を減らし、ロックの保持時間とエスカレーションを抑える
4. **合流点のインデックスを見直す** — 低基数列のインデックスが合流点なら、その列を書き換えない運用にできないか、インデックス自体の要否を検討する
5. **開始時刻をずらす** — 業務都合が許せば数分のずれでも衝突確率は大きく下がる
6. **残りは受け止める** — 重要でない側に `SET DEADLOCK_PRIORITY LOW` を付け、エラー 1205 のリトライを入れる。「起きない」ではなく「起きても業務が止まらない」形にする

## 注意

- system_health の記録時刻は UTC。JST との対応は 06 の occurred_at_jst を参照。
- デッドロックは SQL Server が自動で検出・解消する（犠牲側はロールバックされ、エラー 1205 が返る）。調査の目的は「頻度を下げ、犠牲になっても業務が止まらない形にする」ことで、ゼロ保証ではない。
- 本番で直接プランを取れない場合は 09（プランキャッシュ）を使う。キャッシュは再起動やメモリ圧迫で消えるので、再現している時に取る。
